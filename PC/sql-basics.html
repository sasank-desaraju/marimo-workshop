What is marimo?

A reactive Python notebook

  • Change a cell, and every cell that depends on it reruns automatically
  • Notebooks are stored as plain .py files
  • Built-in UI elements, SQL cells and interactive charts
  • The same file runs as a notebook, an app, a script or slides
  • Runs locally, on molab, or in the browser through WebAssembly

Every widget in this deck is a live marimo cell running in your browser

Your first reactive cells

In marimo

The second cell reads x.value, so moving the slider reruns it. There are no callbacks and no Run button

How reactivity works

marimo reads each cell to find the names it defines and the names it reads, and builds a dependency graph

  • A cell reruns when anything it reads changes
  • Each global name is defined in one cell
  • Delete a cell → its variables are deleted too
  • _name variables are private to their cell
  • Cells run in dependency order, not page order

A notebook is a Python file

import marimo

app = marimo.App()


@app.cell
def _(mo):
    yob = mo.ui.range_slider(1935, 2005, value=[1950, 1975])
    yob
    return (yob,)


@app.cell
def _(con, mo, yob):
    where_df = mo.sql(f"""
        SELECT person_id FROM person
        WHERE year_of_birth BETWEEN {yob.value[0]} AND {yob.value[1]}
    """, engine=con)
    return (where_df,)
  • Each cell is a function: its arguments are what it reads, and its return is what it defines
  • marimo writes this for you; you just edit cells
  • Git diffs are clean: there are no outputs or execution counts in the file
  • python notebook.py runs it as a script
  • import it like a module, or test it with pytest

The running example: OMOP

To show marimo off, we need real-looking data. We’ll use a synthetic OMOP CDM extract in DuckDB

  • Every OMOP site uses the same tables and columns
  • Clinical facts live in event tables; their names live in concept
  • Concept IDs are real (SNOMED, RxNorm, LOINC); people, dates and values are simulated

In marimo

One hidden cell builds con, run() and the colour palette. Every other cell in the deck depends on it

SQL cells: mo.sql

SQL is a first-class cell type in marimo

  • Write plain SQL; marimo runs it on the engine you choose (here, the DuckDB connection con)
  • The result is a DataFrame you can use in Python
  • {python_expressions} inside the query make it reactive
  • Without an engine, SQL can query Python DataFrames by name
# what a SQL cell looks like in the .py file
person_preview = mo.sql(f"""
    SELECT person_id, year_of_birth
    FROM person
    LIMIT 6
""", engine=con)

SQL: FROM names the table, SELECT picks columns, LIMIT keeps the preview small

Running marimo

# editable notebook, isolated env from the file header
uvx marimo edit --sandbox sql-basics-marimo.py

# the same file as an app (code hidden)
uvx marimo run --sandbox sql-basics-marimo.py

# or as a plain script
uv run sql-basics-marimo.py

# a static web page that runs Python in the browser
uvx marimo export html-wasm sql-basics-marimo.py -o docs

# bring an existing Jupyter notebook over
uvx marimo convert notebook.ipynb -o notebook.py

Only in the native editor

  • SQL cells with a schema browser for con
  • A dependency explorer that draws the cell graph
  • mo.ui.dataframe and mo.ui.data_explorer for no-code exploration
  • Vertical, grid and slides layouts for the same notebook
  • molab: open any notebook on GitHub in the cloud

Recap: the marimo toolkit

Idea API Slide
