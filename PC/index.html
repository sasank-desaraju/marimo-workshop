Why another notebook?

Jupyter notebooks are great for exploring, but the notebook you see is not always the program that runs

  • Cells can be run in any order
  • Deleting a cell doesn’t delete its variables
  • Widgets only update the cell they live in
  • .ipynb is JSON with outputs inside, so git diffs are noisy

For teaching, that means a student’s notebook can show results that its code no longer produces

In a study of ~1.4 million GitHub notebooks, only 24% ran without errors and only 4% reproduced their saved results

Pimentel et al., MSR 2019

marimo’s answer: make the notebook a reactive program. Each cell declares what it reads and defines, and marimo keeps every output consistent with the code

How marimo runs a notebook

marimo reads each cell’s code to find the names it defines and the names it reads. That gives a dependency graph

  • Change a cell → marimo reruns everything that depends on it, and nothing else
  • Each global name is defined in one cell
  • Delete a cell → its variables are deleted too
  • UI elements (mo.ui.*) are just variables, so interacting with one reruns the cells that read .value

Move the slider (orange) and only the blue cells rerun

## UI elements and `.value`

```{python .marimo}
#| echo: true
yob = mo.ui.range_slider(1935, 2005, value=[1950, 1975], label="Year of birth")
yob
```

Markdown with code blocks. Quarto owns the layout (slides, columns, theme); engine: marimo makes the blocks reactive cells that run in the browser

# /// script
# dependencies = ["marimo[sql]", "duckdb", "altair"]
# ///
import marimo
app = marimo.App(css_file="omop-marimo.css")

@app.cell
def _(mo):
    yob = mo.ui.range_slider(1935, 2005, value=[1950, 1975], label="Year of birth")
    yob
    return (yob,)

@app.cell
def _(con, mo, yob):
    where_df = mo.sql(f"""
        SELECT person_id FROM person
        WHERE year_of_birth BETWEEN {yob.value[0]} AND {yob.value[1]}
    """, engine=con)
    return (where_df,)

Plain Python. Each cell is a function: its arguments are what it reads, its return is what it defines. Git-friendly, importable, and it runs with python file.py

Which one, when?

Quarto

  • You’re presenting or publishing
  • You need full control of layout and theme
  • Readers should see results, not edit code

marimo

  • Learners should run and change the analysis
  • You want reproducible, git-friendly notebooks
  • The notebook should also work as an app

Jupyter

  • You’re exploring on your own
  • You need a Jupyter-only extension or kernel (R, Julia)
  • Your platform already runs on .ipynb

For this course: teach from the Quarto deck, practise in the marimo notebook, and use the Jupyter version to see what reactivity saves you
